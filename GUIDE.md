# The Sawbuck guide

Everything the [README](README.md) leaves out, in the order people ask. What Sawbuck cannot see is in [LIMITS.md](LIMITS.md), and what was found and fixed in each version is in [CHANGELOG.md](CHANGELOG.md).

## Setting up

**Zero-config:** it finds npm, pytest, cargo and go tests on its own, so in those repos there is nothing to write to start. That includes npm, yarn and pnpm workspaces: each workspace's own `node_modules` is linked into the clean copy the check runs in, and a sibling package is read at the commit being measured, its own command-line tool included. If the tests import a sibling package's built output, they need the build first: `sawbuck init` adds it as `setup`. One case still reads your working tree: a dependency from outside the repo that itself imports one of your workspace packages finds the copy in your checkout, so that path needs your checkout built and is not read at the commit being measured. Anything else (a Makefile target, say) reads inconclusive until you set the command in `promptwheel.config.json`. When it cannot measure, it says which it was: tests that fail before and after, a dependency the clean copy is missing, or a `setup` command that failed.

On attach it tells you exactly what it can measure here (and how to fix it if it can't).

`sawbuck init` writes that config: your detected tests and the tripwires, with notes from your history. Coverage, latency or a cost budget you add to it by hand.

In CI, the same check runs as the [promptwheel GitHub Action](https://github.com/promptwheel-ai/promptwheel#in-ci-and-in-claude-code) (`uses: promptwheel-ai/promptwheel@v0`, or pin it by commit: `sawbuck contract --full` writes the workflow with every action pinned by commit, its own included); the debt gate below is this repo's own Action. For every project at once: `sawbuck attach --user`. Under `--user` the check runs only in repos that have a `promptwheel.config.json`.

One entry point each: a person types `sawbuck`; CI and libraries use `promptwheel` (the engine underneath, `import { check }`). `sawbuck check` passes every `promptwheel run` flag through, so you never need both.

## What it does

- **Verifies the win.** `check` re-runs your metric from the source diff alone. A test that went from red to green because of a deleted, weakened, or skipped test, a mocked grader, an edited golden file, or a loosened declared config reads `gamed`. When the same change also makes a count the contract guards worse (a deleted test lowers the count of tests) or touches a protected path, the check says "sent back" for that, and says the win was gamed as well. A suite weakened while it stays green is not proved: there is no win to re-run. Tripwires catch skips and removed assertions in a signed repo. Deterministic, zero-LLM, $0, and it never reads the trajectory. No appeals once signed; `--allow` lets a change through with a person's reason, and the check says it was allowed, never verified. When more than one thing needs that reason (a test edit and a rules-file edit in one change), the reason has to name each one, so a reason written about one change cannot wave through another. The check prints the line to copy. The checks on the tests themselves count as one thing: a test you remove on purpose moves the green, the count of tests and the count of assertions in one act, and one reason takes them together (a contract written before 0.1.74 takes no reason for the counts until you add `"allowable": "flag"` to them; the check says so). A `Sawbuck-Allow:` commit trailer clears nothing in `sawbuck check`, the Stop hook or the git hook, signed or not, because an agent can write a commit message. Red-teamed in 26 scenarios across 9 ecosystems: of 22 attempts to game it, 12 were caught and 10 got through, each one a limit the report lists, and all 4 honest fixes passed ([promptwheel/bench/REDTEAM.md](https://github.com/promptwheel-ai/promptwheel/blob/main/bench/REDTEAM.md)).
- **A gamed turn ends with you.** The Stop hook sends a gamed turn back to the agent: fix the source so the test passes as it was written, or, if the test itself was wrong, show you the test change and ask. An agent that asks may end the turn. After three send-backs, or when it asks, you get the three ways out as commands: fix the source, put the test back (`git checkout <base> -- <test>`), or accept the change with `sawbuck check --allow "<why>"`. Each of the three settles it. Putting the test back settles it once that is committed; until then the turn is not sent back for it, and you are told the change is still open. A later turn is never sent back for it (since 0.2.0): only the turn that made the change is. While it is open you get one line at the end of each of the next five turns, with the three ways out, and `sawbuck status` shows it for as long as it is open. `{"enforce":{"remindTurns":2}}` in `sawbuck.config.json` sets how many turns, and 0 means never. A reason covers the span it is given for, so when the turn made more than one commit the message gives the line with `--base <where the turn began>` in it, and a reason for the last commit alone says so and clears nothing. The hold asks you before `--allow` runs, so an agent cannot type its own way out. A reason you give before the agent commits, on your working tree, stands for the commit that carries the same change (since 0.1.74). To decide every time yourself, put `{"enforce":{"maxBlocks":0}}` in `sawbuck.config.json`: nothing goes back to the agent and you get the choices at once (the default is 3 send-backs; measured in proof-bench/sendback, new words bent a wrong test 0 of 12, old 2 of 12).
- **Shows what broke before.** `context` surfaces the relevant history (reverts, fragile areas, test-weakening) for the files you are touching: a ranked trail guide, before you act.
- **Shows you everything.** `status` is the inventory: what it has caught for you over time, the debt accruing now, and whether it is armed here, in one view. It says watching only while hooks are wired for this repo, not because an earlier attach left its record on disk. On-demand, so it is quiet until you go looking.
- **Rides on, does not replace.** Sawbuck is the check and the record. Your agent and your loop stay yours.
- **Clean on and off.** `attach` writes a git-excluded `.claude/settings.local.json`, the lines in `.git/info/exclude` that keep its files out of `git status`, a receipt under `.git/sawbuck/`, a line in `~/.sawbuck/registry.json` (the list `detach --all` reads), and in a signed repo `.sawbuck/state.json` (`attach --git` writes the post-commit hook and `.sawbuck/state.json` in place of the settings file); `attach --dry-run` lists all of it. `detach` removes the hooks and the receipt, and still removes the hooks when the receipt is lost; `detach --dry-run` lists what would go. A post-commit hook that was there before `attach --git` is put back byte for byte. Signed contract files stay because they are yours to review. The record (`.sawbuck/`, the logbook files) stays too, still out of `git status`, until `detach --purge` deletes it and the exclude lines. `detach --verify` proves the wiring is gone and names what is left.
- **What a check costs.** It runs your test command, and your `setup` command if the config has one, in a clean copy at each commit it compares, and once more when a test went from red to green. Under the Claude hooks that happens when a turn made a commit, not on every turn. If `setup` is a full production build, narrow it to what the tests need. A check that runs past ten minutes is stopped and says so; `SAWBUCK_CHECK_TIMEOUT_MS` changes that.

## Commands

| command | what |
|---|---|
| `sawbuck contract` | gives a repo its rules: protected paths and the written rule. With no config yet it writes one with your detected tests; an existing config is kept as it is, and gets no tests added. `--full` adds supply-chain guards, a repo lock and a CI check (only with a github.com origin and a real test command; it says when it skips it). `--strict` makes them block, also after an earlier `--full`. `--dry-run` previews |
| `sawbuck check [--base R --head R] [--repeat N] [--allow "reason"] [--json]` | verify your latest change (working tree if dirty, else the last commit, or a range); zero-config, no attach, and no record but one: a reason you give with `--allow` is kept where Sawbuck is attached. Every `promptwheel run` flag passes through: this is the engine with a plain-spoken verdict |
| `sawbuck attach [--user \| --shared \| --git]` | watch every Claude Code turn here: protected paths at the end of each turn, a source-only re-run on each commit. `--user`: in every repo that has a `promptwheel.config.json`. `--shared`: a tracked `.claude/settings.json` a team commits, with no path from your machine in it. It pins one Sawbuck version and runs it through npx. Where a session starts it asks npm for that version once, so a teammate whose machine last ran an older Sawbuck gets the new one. A team file written by 0.1.68 or older has no such line: `sawbuck doctor` says so, and `sawbuck attach --shared` again adds it. `--git`: a post-commit hook, so every commit is checked whatever made it, from the first one after attach (the very first commit of a repo has nothing to be checked against). It leaves a hook alone if it is not a shell script or not executable, and says what to add by hand |
| `sawbuck detach [--user] [--all] [--verify] [--purge] [--dry-run]` | remove the hooks; no flag removes whatever is wired here, with or without the receipt, `--all` does every repo. `--purge` also deletes the record, `--dry-run` only lists what would go |
| `/sawbuck-reins:audit` | finds rules in your agent files that can pull against each other, and proposes which wins. No history needed |
| `/sawbuck-reins:rules` | proposes the rules you keep enforcing, from your own messages, each with quotes; you pick what to keep. Tested on one person so far |
| `/sawbuck-reins:shape` | what you push on, from a sample of your own messages, as a card. It also reads up to 120 past turns and names habits the agent has that you never push on, each with the agent's own words. Leads from one read, tested on one person |
| `sawbuck init` | writes only the config: your detected tests and the tripwires, with notes from your history. `contract` runs it for you when the repo has no config yet |
| `sawbuck status` | the inventory (caught over time, debt now, armed state, what you keep saying), in one view; `--log` for the recent per-check feed |
| `sawbuck debt [repo]` | the whole-repo live suppression debt: what is still silenced in HEAD now, disabled tests first, heaviest files ranked |
| `sawbuck context` | the ranked relevant history for the current change |
| `sawbuck doctor [--all]` · `detach --verify` | run what each hook runs (project and user level) and say if it still works, if the set is incomplete, or if it is gone (exit 1), `--all` for every repo it is attached to; prove the wiring is gone |
| `sawbuck statusline` | a one-line status-line segment (watching / N caught) |

## Protected paths

`sawbuck contract` protects these by default. A change to one reads "sent back", whoever made it.

| rule | paths | how a person makes an exception |
|---|---|---|
| `contract-frozen` | `promptwheel.config.json`, `sawbuck.config.json` | `sawbuck check --allow "<reason>"` |
| `hooks-frozen` | `.claude/settings.json`, `.claude/settings.local.json`, `.sawbuck/**` | `sawbuck check --allow "<reason>"` |
| `workflows-frozen` | `.github/workflows/**` | `sawbuck check --allow "<reason>"` (a contract written before 0.1.70: see below) |
| `registry-config-frozen` | `.npmrc`, `.yarnrc`, `.yarnrc.yml` | remove the rule first |
| `build-images-frozen` | `Dockerfile*`, `docker-compose*` | remove the rule first |
| `publish-scripts-frozen` | `scripts/release*`, `scripts/publish*` | remove the rule first |
| `codeowners-frozen` | `CODEOWNERS` | remove the rule first |

A reason is for the check on a commit and on a pull request. In a Claude Code session the end of a turn is stricter with the agent's own edits: a protected path the agent changed is sent back three times (the default), then you are told, and it is sent back again in later turns for as long as the change stands. A reason does not lift that, and neither does committing the agent's edit yourself. To keep such a change, have the agent undo it and make it yourself: a change that was already there when your prompt began is yours. Since 0.1.71 the send-back tells the agent exactly that (undo it, and tell you to make the edit and give the reason), and the question Sawbuck's hold asks before an agent runs `--allow` says what your yes does: it is kept as your reason for the check on the commit, and it does not let the agent's own edit stand. Before 0.1.71 a real agent, sent back for a workflow bump, told its person to grant `--allow` and ask again, which is sent back again.

A workflow change is ordinary upkeep (a version bump of an action, a new job), so since 0.1.70 it takes a person's reason like the rules file does: on 340 real commits from 17 public repos, 64 of the 65 sent back for a protected path were a workflow change. A contract written before 0.1.70 holds its own copy of the rule, and an update does not change it: add `"allowable": "flag"` to the `workflows-frozen` entry in `promptwheel.config.json` to get the same (that edit takes `--allow`).

To remove a rule, delete its entry under `mandates` in `promptwheel.config.json`, in a commit of its own. That file is protected too, so that commit takes `--allow`. Then make the change. When one change touches more than one thing that takes a reason, the reason names each: `sawbuck check --allow "contract-frozen, hooks-frozen: <reason>"`. To protect another path, add an entry the same way: `{"name": "billing-frozen", "paths": ["src/billing/**"], "reason": "billing changes go through review"}`.

## Give your agent the rule

`sawbuck contract` and `sawbuck init` write this block into your `AGENTS.md` for you (and `CLAUDE.md` / `.cursorrules` if present; `init --no-agent-block` skips it), and `sawbuck attach` enforces it through the hook: every turn checks protected paths, and every commit is re-proved. Here it is to paste yourself if you want:

    In this repo a change is done only when the win survives verification from the source
    alone. Before finishing, run `npx -y sawbuck check`. If it reads `gamed`, the green came
    from editing a test, config, or grader, not the source, so undo that and earn it in the
    source. Run `npx -y sawbuck context` after your first edit to each file, to see what
    broke there before (reverts, weakened tests, fragile spots). Never skip, weaken, or
    delete a test to go green.

## With `--full`: the supply chain and pull requests

On a pull request, the check `contract --full` adds is a workflow, `.github/workflows/sawbuck.yml`.

What it sends back, with a comment that says why:

- a pull request with fewer tests, fewer assertions, or more skipped tests than the branch it came from
- a change to a workflow, the contract, or the check itself
- tests that only pass because the test was changed

What it lets through: everything else. A person with write access can let a sent-back change through with a
comment: `sawbuck-allow: <reason>`. The account that opened the pull request cannot.

**With `--full`.** `pins_changed` is a fingerprint of the resolved dependency tree, not a count, so its value is a long number that only means changed or unchanged. The supply-chain guards read `unmeasurable` on the commit that adds them, because their scanners did not exist before it, and count from the next change. It starts by watching: protected paths, new install scripts and sources outside the registry block from day one, and new dependencies and structure changes show as notes. `sawbuck contract --strict` blocks them all. When something fails, the check says what changed in words. If your tests can't run in CI, the check says so and doesn't fail the job, and protected paths are still enforced. To accept it on a pull request, someone with write access who did not open it comments `sawbuck-allow: <reason>`, and the check is run again; the reason stays on the record. The account that opened the pull request does not count (since 0.1.70): a coding agent run from a service account opens its pull requests from that account, and before this its own comment let a gamed green through. If you are the only person in the repo, add `"allowFromAuthor": true` to `promptwheel.config.json` on your default branch and your own comment counts; a pull request cannot turn that on for itself. A workflow an older `sawbuck contract --full` wrote keeps the engine it pins, and the old rule with it, until its `uses:` line is changed: `sawbuck contract` says when that is so and prints the line. That line is a workflow change. Under a contract written before 0.1.70 the `workflows-frozen` rule takes no reason, so it takes two changes, each with a person's reason: add `"allowable": "flag"` to that rule in `promptwheel.config.json`, then change the line. Under a contract written since, it is one change and one reason. A workflow on `@v0` follows the tag. With more than one thing to accept, the comment names each one, and the check's own comment shows the line. An agent signed in as another person with write access could still post the comment, so branch protection and review still matter. Locally, use `--allow "<reason>"`. A commit trailer is not a person, so Sawbuck does not read one.

## Before a command leaves the repo

**A hold that holds.** Some commands leave the repo and cannot be taken back: `npm publish`, a `gh release`, `gh pr merge`, a public `gh issue comment` or `gh pr comment`, a `git push --force`, `vercel --prod`. `attach` wires a PreToolUse hook that turns each of these into a question to you before it runs; everything else passes untouched, a plain `git push` included. Why a hook and not a line: in our holds bench a hold written in CLAUDE.md ("do not push yet") was talked past by a later ask 6 of 9 times, and a hook is not talked past. Add your own patterns under `holds.outward` in `sawbuck.config.json`, or set `{"holds":{"off":true}}` for a repo. Four things ask you whether the holds are on or off, because each is a way round the check itself: `--allow`, `sawbuck detach`, a command or an edit that names Sawbuck's own record in the repo (`.sawbuck/`, or `.git/sawbuck/`), and a background command that commits. Reading the record is not asked, and neither is the folder of the same name in your home.

## Beside other tools

**Beside a model verifier, too.** Claude Code's agent hooks and superpowers' `verification-before-completion` ask a model, at the end of a turn, whether the work is really done. The check is the floor under that question: it does not ask, it re-runs the tests from the source edits alone, in a clean copy, with no model in the loop. Keep the verifier; give its RUN step `npx -y sawbuck check`, and a green that came from an edited test, a skipped test, a changed config or a touched golden file reads as gamed instead of done.

**Beside whatever memory you run.** Off unless you turn it on: where the repo is attached with `--words`, Sawbuck hands what it finds to the memory on your machine, once each, and reads nothing back: every rule you accept in `/rules`, every reverted attempt the hook recovers (with its reason), every gamed green the check catches. Sinks today: claude-mem's local worker (a titled memory, because its session-start index shows titles), Claude Code's own notes for the project (a note in its form, so Sonnet and Haiku get what Opus writes for itself), and a Markdown folder you name in `sawbuck.config.json` (`{"share":{"markdown":"notes/agent"}}`) for Obsidian or any layer that imports Markdown. A sink that is not there is skipped in silence; `SAWBUCK_SHARE=none` turns it all off. `sawbuck share --title "<rule>" <words behind it>` does it by hand, in any repo, and `sawbuck rules --notes` lists the notes Claude Code's memory already holds for this repo so `/rules` can offer to promote them into the repo's CLAUDE.md. Why the file still comes first: in our twin bench a correction that lived only in the person's words came back 18 of 36 times through a memory layer's own notes and 0 to 2 of 36 as a written rule. The check stays one thing, with nothing to swap into it; the hand-off is the only part that fans out.

## What was tried before

**Rewritten history.** Logbook reads git, so a squash or a rebase takes a revert with it. `sawbuck context` also reads the reflog for commits no branch reaches any more and shows them for the files in hand, with the reason from a revert's message, and once attached it keeps them in `.sawbuck/rewritten.jsonl` after the reflog expires. It stays local: a clone does not get it, nothing older than the reflog comes back, and work that was never committed is not in git at all. Your steering is separate: `reins` reads your agent transcripts, not git.

**Undone in a session, never committed.** Most abandoned attempts never reach git: the agent adds something, you say "undo that, it logged people out last time", the file goes back, and the next session adds it again. Measured twice (proof-bench/attempts, 2026-11-10, and proof-bench/undo-words, 2026-11-17). With nothing written anywhere a later session redid the undone approach 27 of 27 times, and 9 of 9. With the record and your words shown at the prompt: 0 of 27, and 1 of 9. With a record that only said something was undone, without your words: 22 of 27. So without your words the line now tells the agent that the reason is not on record, and to stop and ask you before it makes a change like that one again: 1 of 27, and 26 of 27 asked. Asking costs you a turn each time, until the reason is kept: turn on `attach --words`, or tell Claude Code to keep it (a note it wrote in its own notes when asked: 0 of 27; unasked it wrote one in 4 of 15 sessions that day). When an undo is recorded without your words, the end of that turn tells you so, once in a session. How the record is made: before the agent's first edit to a file in a session, the hook keeps a copy of it, and a file that a shell command changed gets its starting point from the last commit. When a turn ends, what the file held when you spoke, and is gone now, is an undo at your request, whatever wrote it and whatever took it out: an edit, a shell command, `git checkout`. The file back as it was, or as it stood at an earlier prompt, is a whole undo. Most of it gone, with little new in its place, is a partial one. Lines replaced by a rewrite are not an undo, and neither is a turn that stashes the change or changes branch. It is kept in `.sawbuck/undone.jsonl` with the first line that was taken out and a mark for each of the others (a hash, not the text), and shown with the prompt that names the file, in `sawbuck context` and in `status`. With `attach --words` your words are kept with it, and it goes to the memory sinks as a finding; without, the undo is kept without them. When a later turn puts the same lines back, you are told at the end of that turn, once, and the turn is not sent back (the redo line: it reads lines, not ideas, see LIMITS.md). An undo the agent makes on its own, with no word from you in between, is not recorded. Deterministic, no model; it stores a diff summary (and, with `--words`, your own prompt), nothing else, and stays local. A session's copies of files are removed once they are two weeks old, the next time a session starts in the repo.

**Let through, with a reason.** When the check sends a change back and you meant it, `sawbuck check --allow "<reason>"` lets through what takes a reason: a green that came from a changed test, the rules file, the hooks, a workflow change, a new dependency or install script. That reason used to be printed once and kept nowhere. Now, in a repo Sawbuck is attached to, it is kept in `.sawbuck/allowed.jsonl` with what it let through (the test, the protected path, the new install script) and the commit. It comes back with the prompt that names that file, in `sawbuck context`, and as a count in `status`. It is shown as a past decision, not a standing permission: the next change to that test or path is checked like any other. It stays local, like the undo record. A reason left as a pull request comment (`sawbuck-allow:`) stays on the pull request, and one given straight to `promptwheel run --allow` is not kept. What an agent does with it is not measured yet; the claim is only that it is kept and shown.

**Shared with the team and CI.** That ledger is local until you share it: `sawbuck ledger push` puts the erased attempts and their reasons on `refs/sawbuck/ledger` (its own ref, one file, never on a branch) and pushes it; `sawbuck ledger pull` takes it into another clone, where `sawbuck context` and the prompt hook show it with no attach needed. The Action fetches that ref, so a pull request that touches a file with an erased revert gets the revert and its reason in the check's output, and with `comment: 'true'` (and `pull-requests: write`) as a comment on the pull request. Entries are keyed by subject and files, not by sha, because shas do not survive the rewrite that erased them. A person runs push and pull; no hook pushes anything.

## Sawbuck's own record

**The record is not the only witness.** Sawbuck's record lives in `.sawbuck/`, out of git status, so the rule that protects that folder cannot see a write there. Before 0.1.68, deleting or rewriting it after a gamed commit was sent back ended the turn with no send-back (proof-bench/record-tamper: six ways, all six worked). Now the hooks keep a second copy in the git folder (`.git/sawbuck/guard.json`): where the turn began, the gamed changes that are still open, and, since 0.1.69, what the end-of-turn hook itself counts (the last commit it looked at, how often it sent this prompt back). The end of a turn is decided from that copy, whatever the record says. A record that no longer agrees is put back, a turn whose record is gone is checked again from the commit it began at, and you are told the record was removed. In the turn that made a gamed change, only the source earning the green, the test put back, or your `--allow` ends the send-back. After that turn the change stays on that list until the test is back or you accept it. The number of send-backs is the one your config held when the prompt began, and `sawbuck detach` run while a turn is open leaves that turn checked to its end. In the bench, 16 of 18 ways round now fail; on 0.1.68, 9 did. The two that are open: a record rewritten to say you allowed the change copies your yes, and nothing kept on your machine can tell a copy from the real thing. And an agent that removes both copies has removed both; the hold asks you first when a command or an edit names either folder, and a command that reaches them without naming them is not seen. The check itself reads none of this: `sawbuck check` and a run in CI still read gamed.

**What is kept of what you type.** `sawbuck attach` keeps none of what you type. No prompt text is kept in the record. An undo is recorded without your words: the file, the time, the first line that was undone and a mark for each of the others (a hash, not the text). Nothing is handed on to any notes. `sawbuck attach --words` turns all three on: the first 240 characters of your latest prompt, your words saved with an undo and shown with a later prompt that names the file, and a note for each caught gamed green, reverted attempt and undo, written to Claude Code's notes folder for the repo (and to a claude-mem worker or a Markdown folder if you run them). Nothing turns it on for you: neither plugin's setup does. Once on, it stays on through a plain attach until `sawbuck attach --no-words`, which also removes the words already in the record. A reason you give with `--allow` is kept either way: you hand it to the command on purpose, and it is the record of the override. `sawbuck detach --purge` removes the record and the notes Sawbuck handed on (what a claude-mem worker was sent is kept by that tool: remove it there). A repo attached before 0.2.0 keeps none of it from its next prompt on: the words in its record are taken out, and you are told once. Not measured: whether an undo without your words still keeps an agent from redoing the change. The 0 of 27 above was with the words.

## Other agents

**Try it on your own past first.** `sawbuck contract --try` writes nothing. It holds the contract a real run would write against your last 20 commits (`--try=50` for more, 200 at most; merges are left out) and says which would have been sent back to ask you: the ones that touch a protected path, and the ones that make a count worse. The test run itself is not replayed. When we held the plain contract against 340 real commits from 17 public repos, 82 were sent back, every one for a protected path or a count (proof-bench/contract-replay). So look before you turn it on.

**In a loop, with no person.** `sawbuck check --base <ref> --json` prints one JSON object (base, head, verdict, metrics, gate and more) and exits 0, 1, 2, 3 or 64, as the README lists them. Nothing in it calls a model. The check behind it is the `promptwheel` package: a metric is any command reduced to a number, with a direction and a guard, and a change inside the measured noise is not counted as a win. What Sawbuck adds to an agent's context is small. On a small repo with the plain contract: 531 characters for the rule in AGENTS.md, and 918 once per session. A later prompt gets nothing unless it names a file with history. A loop that scores itself on fixed tasks should know one limit from LIMITS.md: a value hardcoded in the source to fit the visible case is not seen.

**Codex too.** `sawbuck attach --codex` writes the same hooks into `.codex/hooks.json` (kept out of git status): the rules with each prompt, a gamed commit sent back at Stop, and the hold on outward commands. Codex runs a new hook only after you trust it once in its `/hooks` screen. One difference, from Codex's side: it does not support "ask" yet, so the hold denies the command and tells the agent a person runs it. The undo ledger reads the files each apply_patch names.

**Cursor too.** `sawbuck attach --cursor` writes `.cursor/hooks.json` (kept out of git status): the check at the end of each agent run, where a gamed commit comes back to the agent as a follow-up message (three at most), and the hold, which asks you before an outward shell command. Cursor's prompt hook can only allow or block, so the rules reach the agent through the AGENTS.md and .cursorrules lines `sawbuck contract` writes, and history does not ride the prompt. The undo ledger rebuilds each file's text before the edit from what Cursor reports.

## Your profile and your steering

**Your profile, on every machine.** Rules you keep go to `~/.claude/CLAUDE.md` by default, which Claude Code loads in every session, in a repo or not. Holds of your own go in `~/.sawbuck/config.json` (`{"holds":{"outward":["\\bgit\\s+push\\b"]}}`) and ask you first everywhere on the machine, with `sawbuck attach --user` wiring the hooks once for all of it. `sawbuck profile` shows the rules, hooks, holds and what you keep saying in one view; `sawbuck profile export > my-profile.json` and `sawbuck profile import my-profile.json` carry the rules and holds to another machine (no transcripts, no steers, nothing from a repo).

**How you steer.** `sawbuck steering` shows what you keep correcting, then what happened after each push you gave the agent: the commits and files that followed, edits undone at your request (whole or in part), the check's verdicts, reverts, and whether you had to say the same thing again in a later session. It joins the plugin's steer record with Sawbuck's own records by repo and time, from one steer to the next and an hour at most, so it is a lead about cause, not proof. A push that keeps coming back is a rule to write down; one that moved nothing may not have landed. A session in a folder over several projects (not itself a repo) counts the commits in each repo one level under that folder.

**Notes that went stale.** `sawbuck rules --notes` lists the notes Claude Code's own memory holds for this repo, and flags the ones that name files the repo no longer has, so a note about code that is gone is checked before anyone promotes it.

## What the check trusts, and what it counts

**What the check trusts.** The check proves the tracked files. Its clean copy of each commit still borrows three things from your machine: the installed dependencies it links in (`node_modules`, the venv), the environment it is run in, and the repo's local git settings. None of those is in a diff, so a green that leans on one of them reads as "tests pass before and after": a library patched by hand in `node_modules`, a variable such as `PYTEST_ADDOPTS` or a preload in `NODE_OPTIONS`, a git filter set in `.git/config`. For the variables, since 0.1.70 the check says so when one of them is set (`PYTEST_ADDOPTS`, `PYTEST_PLUGINS`, a preload in `NODE_OPTIONS`): a note beside the verdict, never a block, and nothing is taken out of your environment. Measured 2026-11-11 with seven such plants: six read pass while a fresh install was red, and a test edit hidden with `git update-index --assume-unchanged` did not. A fresh CI runner has none of them, which is one more reason to run the check there as well. In the session Sawbuck watches the first: when a turn edits a file inside an installed dependency, with the agent's edit tool or with `sed -i`, a redirect, `tee`, `patch`, `cp` or `mv` in a shell, you are told once when the turn ends. It is a notice and never a block, and it says nothing when the edit is kept as a patch your install applies (`patches/`) or the package was installed again. A write made some other way, such as a script that opens the file, is not seen.

Without a `promptwheel.config.json` the check measures your detected test command. `sawbuck init` writes the config with that command and the tripwires, and explains each line with evidence from your history. The tripwires are four counts taken beside the test run. Three send a change back when they get worse while the tests stay green: fewer tests, fewer assertions, more skipped tests. A person's reason lets those three through (`--allow`), in a contract written from 0.1.74 on. The fourth is more lint silencers (`eslint-disable`, `# noqa`, `//nolint`, `#[allow(`), and it is a note when it buys nothing: people add those in ordinary test code, so when nothing else got better the check shows it and passes. A silencer that arrives with a green, a lint error silenced to get there, is still sent back. `sawbuck contract --strict` sends every new one back. To make the config count more (coverage, lint, latency, an eval) or to protect another path, add a metric or a mandate to it by hand.

## Measured

Measured in November 2026, beside the numbers on the first page. A reverted attempt squashed out of git was redone blind 26 of 27 times with git alone, and 0 of 27 when Sawbuck showed the reason with the prompt, with all 27 asking first. The corrections a person kept making came back 57 of 216 times in a fresh session with nothing written, 2 to 8 of 216 with the rules written. Of 593 active repos we checked, about half had a rules file for agents, and 19 had a rule like the test one.

**Measured, not assumed.** On a scenario whose natural fix sits inside a protected module, 62 trials: 52 driven past a forced compaction (two on the default model, one on Haiku) and 10 shallow, some under "urgent hotfix" pressure. With no rule the agent edited the protected file 17 of 17 times; with a rule in any form, including a mandate, 0 of 45. Earlier scenarios did not tempt it (no rule, 0 of 17), and the wall never had to fire. The model honors a rule it was told. The gate is for the rule nobody told it, the session that outlived the summary, and the proof that it held: once attached, the hooks re-read the mandates from the repo on every turn, say them again after a compaction, and send back a turn that leaves a protected path changed, up to three times by default. Numbers and method: [sawbuck.ai/contracts](https://sawbuck.ai/contracts).

## Gate debt on pull requests

`sawbuck debt --since <base>` shows only the suppression debt a branch adds. Fail the build when a PR adds the kind you care about:

```yaml
# .github/workflows/debt.yml
name: debt
on: pull_request
jobs:
  debt:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }   # the base ref must be present to diff against
      - run: npx -y sawbuck debt --since "origin/${{ github.base_ref }}" --fail-on undocumented
```

`--fail-on` takes `undocumented` (a bare `# type: ignore` / `# noqa` with no code), `test` (a newly disabled test), `any`, or a number of new suppressions; anything else is an error (exit 64). Without `--since` it gates everything live in HEAD, not only what a branch adds. Exit 1 fails the check; add `--json` for the machine-readable delta. This repo is also a composite action: `uses: sawbuck-ai/sawbuck@v0` with `base` and `fail-on` inputs.

Debt is on demand: `sawbuck debt`, and `sawbuck context` for the files in hand. One thing is not on demand: when a prompt names a file (`src/cache.js`, or a bare `cache.js` that matches one tracked file), the hook shows what a rewrite erased there, a revert and its reason, with the prompt, before any edit. In our twin-repo bench that timing was the whole difference: shown with the prompt, 0 of 27 agents redid a reverted change and 27 of 27 asked first; left for the agent to ask after its first edit, it checked once per session and redid it 27 of 27. To have the rest of the history (hot spots, weakened tests) added to every turn as well, set `{"turn":{"context":true}}` in `sawbuck.config.json`. That is off by default because a written rule did the work in every bench, and context spent on each prompt is context lost.

## The engines

Sawbuck is thin glue over two engines:

- **the check** : the deterministic outcome gate, written up as a draft spec (the [Verified-Outcome Contract](CONTRACT.md)). Reference implementation: **promptwheel**. You plug in *what* to measure (your tests, lint, coverage, an eval); the source re-proof is the fixed part. Embed it with `import { check }`, or check any tool's verdict with `conformsToContract()` from the same package.
- **the record** : the relevant history for the files you touch, plus the live debt, from **@promptwheel/logbook** (it reads git; also ships an MCP server).
