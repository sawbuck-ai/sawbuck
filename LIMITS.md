# What Sawbuck cannot see, and what has not been run

Each limit here is held by a test in [`test/claims.test.mjs`](test/claims.test.mjs), or is something that has not been run, and says so. The short list is on the [first page](README.md).

## The check

- **A suite weakened while it stays green.** It is not proved: there is no win to re-run. Tripwires catch skips and removed assertions in a signed repo.
- **Says what it cannot see.** A gaming move that lives inside the source itself (a value hardcoded to the one visible case, logic keyed to the test environment) is invisible to a source-only re-run, by construction. That limit is in [the contract](CONTRACT.md#3-the-integrity-boundary-what-counts-as-gaming), not hidden.
- **A count that got worse with nothing gamed.** A test deleted from a green suite is said once at the end of a turn and not sent back. The check on the commit and on a pull request fails it until a person gives a reason.
- **A change that swaps a test tool.** When a commit removes a dependency that the earlier tests need to build or run (a lint tool whose settings the build extends, say), the earlier tests cannot be run with what is installed now, and the commit can read `gamed` though its own tests passed before and after. Seen on 1 of 320 real commits in November 2026. Accepting the change with a reason is the way through.
- **What the note on tests taken out does not see.** The note reads each test by its name, with a small reader for each language. A test made from a table in JavaScript, Python or C# has one name, so it counts as one test. A language the reader does not know is not read, and neither is a test written in a way it does not know. A pull request squashed into one commit has no earlier commit to read, and a shallow clone holds none: then the note says nothing. It speaks only when the pull request as it stands adds no tests, so it also says nothing when the tests an earlier commit added are taken out and one other test is added. On a pull request it sends the change back, and a person's reason lets it through. Everywhere else it is a note. The note on two or more named tests gone reads tests the same way, and a rename reads to it as tests gone: the note says so. Both notes say nothing where a test file the change touched is too big to read (over 2 MiB), and the second also where the clone is too shallow to find where the change left its base.
- **What the note on a rewritten test does not see.** It reads the commits of a pull request one by one, so a pull request squashed into one commit gives it nothing to read. A test rewritten in the same commit that changed the source is ordinary work and is not noted, unless an earlier commit had already changed the source without it. A test file the base did not have is not read (tests a pull request added and then took out have their own note). It speaks only where the base branch's tests fail on the pull request's source. A test file moved or renamed reads as one file gone and a new one, and is not read. A clone that does not hold the pull request's commits (a shallow fetch) gives it nothing to read, and so does a pull request of more than 60 commits or a commit that touches more than 2,000 files.
- **Where no test command is found.** `sawbuck contract --full --comment-only` writes the pull request check there too. That check runs no tests. It reads the counts of your tests and the protected paths, and its job summary says it could not measure. A test that fails is not seen there until your test command is in `promptwheel.config.json`.
- **A repo signed `--solo`.** On a pull request the comment of the account that opened it counts, and an agent that works under that account can post it. GitHub cannot tell the two apart. What is kept is the reason, not proof of who gave it.

- **The loop is not known to get better with use.** `sawbuck improve` keeps a change only if it measured better: that is tested. That a later attempt is better for the record of earlier ones is not shown. The test for it exists and has not been run on real work.
- **The loop can fit your own tests.** A loop that keeps what raises a measure will find what raises that measure. The source-only re-run stops the cheapest way (a change to the tests) and no other. Tests the loop never sees are the answer, and Sawbuck does not hold any for you.
- **More turns are more tries.** A run judged over several turns gets several tries at the measure. The best turn is measured once more before it is kept, which stops a win that was noise. It does not stop a loop from fitting the measure: the longer the run, the more that matters.
- **A run that is killed outright cannot put the tree back.** An interrupt (Ctrl-C, a stop signal) does. A kill that cannot be caught leaves the tree as the attempt had it. The next `sawbuck improve` says so, prints the one line that puts the tree back, and deletes nothing by itself.
- **The record is a hint.** It is a file in the repo's git folder. Anything that can write to the repo can write to it, so it never decides a check.

## In a session

- **A change that was sent back is not held when it took its own rule away.** A turn that removes
  every rule from the contract and commits is sent back once, and you are told. The next turn has no rules
  to be sent back by. The same for a contract that is deleted before its first commit and left deleted. What
  holds: the check on the commit and on a pull request, which read the contract as it was before the change.
- **A change the agent makes again in the same turn you undid it.** When you undo a sent-back protected change
  while the agent's turn is still running, and the agent makes it again before that turn ends, you are told at
  the end of the turn and the agent is not sent back. Undo it between turns, and the agent making it again is
  sent back.
- **A committed change you leave on another branch.** A protected change the agent committed is not flagged
  again when you check out another branch and then come back to the first one.
- **Your own edit to a file the agent was sent back for.** If you edit a protected file between turns while it
  still holds a change the agent was sent back for, or commit it with more of your own, the file as you leave it
  is taken as yours, the agent's change in it included.
- **Cursor, after the first send-back.** Cursor's end of a turn has no line for the person, so after the agent is
  sent back once for a change, Cursor may show nothing more about it while it stands.
- **Before a repository's first commit, only the contract is read by name.** A workflow or another protected file
  that a turn stages, puts in the first commit, or deletes or hides while it is untracked is not seen at the end of
  the turn. Reading every file there by content sent back ordinary work (a staged file's edit put back, a pull into a
  new repository), so it was taken out. A pull request reads it.
- **A protected file that git ignores.** An `.npmrc` named in `.gitignore`, say. The end of a turn reads what git
  lists and the contract's own files, so an edit to an ignored file is not seen there.
- **A change that is only staged.** A protected file edited, staged, and then put back in the folder leaves the
  edit in git's index and nothing in the folder. The end of the turn does not see it. A commit that carries it is
  checked like any other.
- **What `sawbuck align` does not see.** It reads what each commit did to the counts and the protected paths. It does not run the tests. It finds where a Claude Code session began from that session's own file, so a session that began in another folder is not found, and the reading then starts at the first commit. More than 100 commits are read as the last 100, and the reading says so. `attach --user` reads no repo.
- **After the turn that did it.** A gamed change is sent back in the turn that made it, up to three times. After that turn it is told, not sent back: you get one line at the end of each of the next five turns (`enforce.remindTurns` in `sawbuck.config.json` sets how many), `sawbuck status` shows it for as long as it is open, and a later turn can build on it. `sawbuck check` on the commit and the check on a pull request still fail.
- **A limit of the turn hook.** The hook re-runs your tests on commits, not on uncommitted work. A test edited to go green and left uncommitted is not sent back at the end of that turn. It is caught when it is committed, and `sawbuck check` reads it on demand, which is what the written rule tells the agent to run before finishing.
- **Work a turn leaves running.** A background task the agent starts can commit after its turn has ended. When the task reports back, Claude Code begins a new turn, and that commit is checked with it as the agent's own (before 0.1.69 it was read as yours and not checked). A commit from a task that is still running when you type your next prompt is read as yours: nothing tells the hook who made it. The hold asks you before a background command that commits.
- **How it tells the agent is asking.** A gamed turn may end when the agent's last message has a question near its end and names the test (or says "test"). That is a reading of words, so an agent can end a turn that way without a real question. It does not settle the change: you get the three choices, and the change stays open (told at the end of the next turns, shown in `sawbuck status`) until the test is put back or you accept it.
- **Another mod can answer for you.** Claude Code mods are not sandboxed: a mod can approve a tool call before you see it. Sawbuck's hold asks before an outward command and before `--allow`, and that question is only yours if no other mod approves tool calls on your behalf. Its protected paths still stop the agent from removing Sawbuck's hooks.
- **Two agents in one folder.** Two sessions working in the same checkout share one record of what was there when a turn began. A protected file one of them changes still sends that one back, and it also sends back the other, whose message says not to undo anything it did not change. Give each agent its own git worktree; the hooks carry into each one, with its own record.
- **An agent that works in a clone of its own.** The hooks watch the repo the session is in. An agent that clones the repo into another folder and works there is not seen at the end of a turn. Some tools that run agents in the background work that way, so that they never touch your checkout. `sawbuck check` run in that clone, and the check on its pull request, still read it.
- **Auto mode and the written rule.** The rule tells the agent to run `npx -y sawbuck check` before finishing. In Claude Code's auto mode Claude Code itself can refuse that command (seen on 2.1.318 in a new session, three times in two turns), and the agent may then tell you the change is unverified. Under Sawbuck's hooks it is not: the end of the turn checks every commit the turn made, whether or not the agent ran the check. `sawbuck status` shows the last check and what it read.
- **A test you changed yourself.** A test you edit or delete yourself and then ask the agent to commit is read as the agent's change, and the end of the turn sends it back until you accept it or put it back. The check judges the change, not who made it. Your reason, given before or after the commit, ends it.
- **What the undo record does not see.** An undo is judged when a turn ends: what a file held when you spoke and is gone now. The file's starting point is a copy kept before the agent's first edit, or, where a shell command wrote the change, what the last commit holds. Not recorded: a change that a shell command wrote and committed, and that was then taken back with `git revert` (the revert is in git's history; taken back with a reset, it is shown as erased). A turn that stashes or changes branch: the lines were set aside, not taken out. A new file git does not track that an earlier session made. A file over 256 KB, or a binary one. At one prompt the newest twenty changed files get a starting point, and the rest get theirs at later prompts.
- **Without your words the agent is told to ask, not why.** By default the record holds that something was undone, not the reason. The line a later session gets tells the agent to stop and ask you before it makes a change like that one again. Measured (proof-bench/undo-words, 2026-11-17): 1 of 27 made the undone change again and 26 asked; a line that only stated the fact had 22 of 27, and no record 9 of 9. The asking has a cost. On an unrelated job in the same file 2 of 9 stopped to ask too. Where the agent already had the reason in Claude Code's notes, 8 of 9 still asked. And a new session asks again, until the reason is kept somewhere.
- **The redo line reads lines, not ideas.** When a turn ends, Sawbuck looks for the lines you had undone. If at least three quarters of them, and two or more, are in the file again, you are told. The same idea written in other lines is not seen: in the same bench the line fired on none of the 32 runs where a later session wrote the undone change again in its own words, and on 3 of 3 where the same change was written back. An undo of one line is not watched, an undo recorded before 0.2.0 has no marks to compare, and a turn that stashes or changes branch is not looked at.
- **A shell line you run inside a session.** Found 2026-11-16 in a real session, and not fixed yet. In Claude Code 2.1.318 a line you run with `!` starts a turn of its own, and the hooks get no prompt event for it. So what your line changed is read as the agent's: your own edit to a protected path, made that way, is sent back once as if the agent had made it, and after that you are told at the end of each turn while it stands. Until this is fixed, make such an edit in your editor or another terminal between two prompts; then it is yours.

## The hooks and the record

- **The activity feed is a record, not a proof.** It sits in your repository's folder, and an agent that writes
  there can write a line in it. A program that shows those lines can say what Sawbuck's hook recorded on this
  machine. The check on a pull request runs where an agent on your machine cannot reach.
- **A repository git cannot read.** A broken line in `.git/config`, or a broken index, and git answers nothing.
  The end of that turn says nothing either. The change is not taken up: it is sent back at the first end of a turn
  after git works again.
- **A limit of the hooks file.** `.claude/settings.local.json` is kept out of git, so taking the hooks out of it shows in no diff, and the check cannot see it. `sawbuck doctor` can: it reads the receipt and says the hooks are gone, or that the set is incomplete (a missing Stop hook, say). `sawbuck attach --shared` avoids it: the hooks go in a tracked file, and a removal shows in git.
- **A limit of the git hook.** `attach --git` pins the hook to the checkout it was attached from, so a commit made in a linked git worktree is not checked. A hooks folder inside the work tree (`core.hooksPath`, as husky sets it) is refused, and attach prints the line to add by hand; `detach`, `doctor` and `status` do not know about a line added that way.
- **A hooks folder every repo shares.** With a global `core.hooksPath` git runs hooks from that one folder, so `attach --git` puts its block there, in a file outside your repo, for the first repo you attach. For a second repo it says the folder is shared and writes nothing (before 0.1.73 it said "already attached", which was not true of that repo). In those repos use `attach` (Claude Code) or `attach --shared`.
- **Two ways round the second copy are open.** A record rewritten to say you allowed the change copies your yes, and nothing kept on your machine can tell a copy from the real thing. And an agent that removes both copies has removed both; the hold asks you first when a command or an edit names either folder, the folder in your home where a turn's beginning is kept when there was no repository (`~/.sawbuck/began/`), or your own holds (`~/.sawbuck/config.json`), and a command that reaches them without naming them is not seen.

## What is judged cannot touch what judges it

Sawbuck judges an agent that runs as you, on your machine, with no wall between them. Held to a list of attacks on
2026-11-21, these are the places where that shows. Each was run.

- **The installed copy can be edited.** Sawbuck runs from files on your machine: where npm, npx or the plugin put it. An agent that runs as you can edit those files, and the next check then runs the edited code. Nothing on your machine can notice: the thing that would notice is the thing that was edited. Run: after a turn rewrote the installed hook, a gamed commit ended the next turn with nothing said, and `sawbuck doctor` from the same copy said OK. What holds: the pull request check, which runs a fresh copy that the agent's machine never touches, or a container around the agent.
- **An installed package that your tests run.** Git ignores `node_modules` and folders like it. An agent that edits a package there can turn a red test green, and no commit shows it: the check reads the same package before and after. Run: the end of the turn said nothing, and `sawbuck check` said "held". What holds: a fresh install, as on a pull request.
- **A file a process changes after the turn has ended.** A process the agent leaves running can edit a file once the end-of-turn check has passed. Nothing is said about it at the end of the next turn. A test changed that way is checked like any other change when a turn commits it. A protected path changed that way is read as yours, because it had changed before the turn began: the end of a turn does not speak of it. The check on the commit does, and so does the check on a pull request.
- **A rule deleted behind another rule.** When two checks in your code cover the same thing and an agent deletes one, no test fails and no count falls. Sawbuck does not see it. What protects should be a protected path in your contract, so that a change to it takes your reason.
- **A filter in git's settings.** A filter set in the repo's git config, or in yours, changes what a checkout holds. A turn can set one so that the commit stores one thing and the check reads another. Run: a commit that broke a test was read as fine at the end of the turn, and by `sawbuck check`. What holds: the check on a pull request, which runs on a clean clone and does not read your git settings.
- **A process that writes into the copy the check measures in.** The check measures in a copy it makes in the temp folder. A process the turn leaves running can write into that copy while it is measured. Run: a commit that broke a test was read as fine. What holds: the check on a pull request, which runs where the agent's processes do not.
- **Closed in this version:** a file named `HEAD`, or named as a commit, no longer makes git refuse the questions the end of a turn asks. A contract that is not yet committed is read by name, so deleting it, hiding it in `.gitignore`, staging an edit to it or carrying one into a first commit is seen.

## Your machine

- **Your git, your settings.** Run on git 2.25 through 2.52, and under what a `~/.gitconfig` commonly holds: no `a/` `b/` prefixes, an outside diff tool, forced colour, signed commits with signatures shown, a global hooks folder, a global ignore file. Before 0.1.71 four of those could change what a check read, and a file whose name holds a byte above 127 (`añadir.js`) was read wrongly under git's defaults: an honest fix there was sent back as gamed, and a new workflow file named that way was not a protected path. Not run: Git LFS, submodules. A Mac and Windows are under "Not run", below.
- **A push where git keeps no log.** When a turn ends, Sawbuck tells a commit the agent pushed from one that came from the remote by git's own log of each remote branch. In a clone that keeps no log of remote branches (`core.logAllRefUpdates` set to `false`), a commit the agent made and pushed in the same turn is not checked when the turn ends. `sawbuck check` and the check on a pull request still read it.
- **Which copy answers.** A line with a version in it runs that version: the plugin's lines, a hook's own path, `npx -y sawbuck@0.2.7 check`. A line without one runs whatever copy your machine holds. If you installed with `npm i -g sawbuck`, that copy answers a bare `sawbuck`, `npx sawbuck` and the rule's own `npx -y sawbuck check`, and it does not update itself; on npm 8, `npx sawbuck` with no global copy keeps the copy of its first run. `sawbuck --version` shows what you have, and `npm i -g sawbuck@latest` moves it to the newest (with `sudo` if that is how you installed it). Run on npm 8 through 11. Since 0.1.73: when an older copy is first on your PATH, `attach`, `status` and `doctor` say so, the agent is given the exact line for the rule's check, and you are told once at the end of a turn; a git hook runs the copy that wired it (before 0.1.73 it asked PATH first, so in a repo wired earlier run `attach --git` again); and the lines Sawbuck gives you to type name their version. Not covered: a copy older than 0.1.73 says nothing about itself, a global copy whose folder is not on your PATH is not seen, and nothing here asks npm whether a newer version is out.

## Not run

- **A real session on a Mac.** The tests ran on GitHub's Mac runner for the first time on 2026-11-16 and 15 failed, all on a folder reached through a symlink. 0.1.74 fixes what that found ([CHANGELOG.md](CHANGELOG.md)). No session has been run on a Mac.
- **The one comment, on GitHub itself.** That the pull request check edits its one comment in place was run with a stand-in for GitHub's command line, not on GitHub. If GitHub refuses the edit, the check posts a new comment instead.
- **Windows.** The tests ran there the same day and about half fail (187 of 382). Not supported yet.
- **Codex and Cursor**, for what was found on 2026-11-16 (a gamed win beside something else, and the ways out of a send-back). Git LFS and submodules.
